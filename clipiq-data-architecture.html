ClipIQ Internal · Architecture Reference

项目 · 分析 · 日志：数据关系全景

从一个 projectId 出发，追踪数据在四个存储层之间的流动

STATUS · REFERENCE DATE · 2026-05-25 CODEBASE · feature/v2
TL;DR
ClipIQ 的数据围绕 projectId 组织，分布在四层：SQLite（项目元数据 + 节点 + 报告，持久化到磁盘）、文件系统（关键帧 / 音轨 / 字幕 / checkpoint，跨分析复用）、React 状态（进度快照 + 日志 + ETA 预算，存活于内存）、Main 进程状态（分析句柄 + 心跳 + 子进程，分析结束即销毁）。点击"重试"时，startAnalysisForProject 清空内存层 + 部分 SQLite 行，但保留文件系统 artifacts；ProgressScreen 挂载后向 Main 进程发起新的 analyzeProject IPC 调用，管线从头启动。

01三个核心实体

理解 ClipIQ 的数据模型只需要抓住三个名词：Project（项目）、Analysis（一次分析执行）、Progress Log（进度日志）。它们之间是 1 : N : N 的关系——一个项目可以被多次分析，每次分析产出一组进度日志。

PROJECT
项目
→ 用户看到的"一个视频"
由 proj-{timestamp} 唯一标识。携带来源（URL / 本地文件）、时长、分辨率、分析配置、状态机位。
ANALYSIS
分析执行
→ Main 进程的一次管线运行
由 activeAnalyses.get(projectId) 句柄代表。包含 AbortController、子进程集合、心跳定时器、Token 账本。结束后句柄销毁。
PROGRESS LOG
进度日志
→ React 内存中按 projectId 累积
每条 ProgressLogEntry 记录 absoluteMs / stage / message / tone / fromCache。上限 80 条，去重后追加。

一个关键设计：Analysis 执行没有独立 ID。它不写入数据库、不做审计追踪。系统只保留"最近一次成功"的结果（nodes + report），重跑时直接覆盖。进度日志也只保留当前运行的——重新分析时先清空，再从零累积。

02四层存储架构

数据按持久性和生命周期分布在四个层。从上到下：生命周期越长、写入代价越高。

各层详细拆解

存储层 位置 存什么 Key 维度 重试时清除
React State AppContext useState 进度快照、日志数组(80 条上限)、ETA 预算、项目列表 projectId 清除
Main 进程 activeAnalyses Map 分析句柄（AbortController + 子进程 + 心跳 + 缓存策略 + Token 账本） projectId 自动销毁
文件系统 userData/projects/{id}/ 关键帧 JPG、音轨 WAV、transcript.json、media-manifest.json、frames-checkpoint.json、analysis-result.json projectId + 文件名 部分清除
SQLite userData/data.db 项目元数据 JSON、分析节点 JSON、分析报告 JSON project_id PK 清除 nodes+reports
GOTCHA
文件系统 artifacts 有意保留。resetAnalysis 只删除 analysis-result.json 和 timings.json，不删 artifacts/、media-manifest.json、frames-checkpoint.json。这是为了让重新分析能跳过耗时的抽帧和字幕识别（复用上次的结果）。但这也是用户"清缓存后重新分析还看到旧日志"的感知来源——那些"恢复进度 · 跳过抽帧"的消息是新日志，只是内容引用了旧 artifacts。

03SQLite 表结构

核心只有三张表，全部以 projectId 为主键或外键。数据列都是 TEXT NOT NULL——实际存的是 JSON 字符串，schema 由 TypeScript 类型定义（src/types.ts）约束。

CREATE TABLE projects (
  id         TEXT PRIMARY KEY,    -- "proj-1716652800000"
  data       TEXT NOT NULL,       -- JSON: Project 对象全貌
  updated_at INTEGER NOT NULL     -- Unix ms
);

CREATE TABLE analysis_nodes (
  project_id TEXT PRIMARY KEY,    -- 1:1 关系，一个项目只保留最近一次结果
  data       TEXT NOT NULL        -- JSON: AnalysisNode[]
);

CREATE TABLE analysis_reports (
  project_id TEXT PRIMARY KEY,    -- 1:1 关系
  data       TEXT NOT NULL        -- JSON: AnalysisReport 对象
);

注意 analysis_nodes 和 analysis_reports 都是 ON CONFLICT(project_id) DO UPDATE——同一项目的多次分析结果是覆盖写，不追加。这意味着历史分析结果不可回溯。

Project.data JSON 关键字段

字段 类型 说明
status string not_analyzed | downloading | analyzing | completed | failed | download_failed
analysisStartedAt ISO string 本次分析开始时间，重试时更新
analysisOptions AnalysisOptions mode (quick/standard/detailed) + density + focus
providerId / model string 发起分析时快照的供应商和模型
lastErrorMessage string? 最近一次失败的错误信息

04文件系统：Checkpoint 与 Artifacts

每个项目在 ~/Library/Application Support/clipiq/projects/{projectId}/ 下有自己的目录。文件分两类：checkpoint 文件（管线中间产物，带版本校验）和 artifact 文件（最终产物）。

projects/{projectId}/
  artifacts/
    shot-001.jpg            # 镜头缩略图
    shot-002.jpg
    ...
    transcript.json         # 字幕识别结果
  media-manifest.json       # checkpoint: 视频检测 + 场景分析
  frames-checkpoint.json    # checkpoint: 抽帧结果
  analysis-result.json      # 最终分析结果 (nodes + report 的备份)
  timings.json              # 各阶段耗时统计
  danmaku.json              # B站弹幕原始数据

Checkpoint 的版本校验机制

每个 checkpoint 文件内含 pipelineVersion 字段（当前值 "mvp-local-2026-05-13"）。加载时只有版本匹配且文件完整（如帧文件在磁盘上存在）才复用，否则从头重跑该阶段。

NOTE
resetAnalysis IPC 只清理 analysis-result.json + timings.json，故意保留 artifacts 和 checkpoint。这就是为什么重新分析时管线会打出"恢复进度 · 跳过抽帧"之类的消息——它检测到了有效的 checkpoint 文件。

05React 内存层：进度 · 日志 · 预算

AppContext 维护三个以 projectId 为 key 的 Map，全局只订阅一次 IPC 事件，避免组件 mount/unmount 导致漏事件。

State 类型 写入来源 上限
progressByProject Record<string, AnalysisProgressEvent> onAnalysisProgress IPC 1 条/project
logsByProject Record<string, ProgressLogEntry[]> onAnalysisProgress IPC（去重追加） 80 条/project
budgetByProject Record<string, AnalysisBudget> onAnalysisBudget IPC 1 条/project

ProgressLogEntry 结构

{
  absoluteMs: number,    // Date.now() — 接收到事件的时刻
  stage: string,         // "本地初筛" | "字幕识别" | "模型分析画面" | ...
  message: string,       // "已抽 12/20 张 · 第 34.5 秒"
  tone: "info"|"ok"|"warn",  // 自动检测：含"失败"/"错误" → warn；含"完成" → ok
  fromCache?: boolean    // 整段命中 LLM 缓存时为 true
}

去重逻辑：追加前比对最后一条的 stage + message + fromCache，完全相同则跳过（心跳消息只更新"已等待"后缀，stage 和 base message 不变时仍可能通过去重）。

06Main 进程：分析句柄生命周期

Main 进程用一个 Map<projectId, Handle> 管理所有活跃的分析。同一项目同一时刻只允许一个分析。

Handle 内部结构

handle = {
  abortController: AbortController,  // 用于中断 fetch / 子进程
  children: Set<ChildProcess>,       // ffmpeg / yt-dlp 等子进程集合
  cancelled: boolean,                // 用户取消标记
  lastProgress: { projectId, progress, stage, message },  // 最近一次 send() 的快照
  lastProgressAt: number,            // Date.now() — 用于心跳检测 idle > 1.5s
  heartbeat: IntervalID,             // 每 2s 重发 lastProgress，防 UI 看起来卡死
  budget: { projectId, budget },     // ETA baseline — 开头算一次广播
  tokenLedger: TokenLedger,          // 各阶段 token 消耗累计
}

无论从 HomeScreen、WorkspaceScreen 还是 ProgressScreen 点击"重新分析"/"重试分析"，都会调用同一个入口：startAnalysisForProject(projectId)。以下是逐步发生的事情：

关键细节

  • 步骤 1-4 是一个 React batch。所有 setState 调用在同一个事件处理函数里，React 18 自动批处理。ProgressScreen 挂载时看到的一定是清空后的状态。
  • 步骤 2 是 fire-and-forget。resetAnalysis 的 IPC 调用用 .catch() 忽略错误，不阻塞后续步骤。理论上存在微小的时序窗口，但实际不影响：resetAnalysis 清的是 SQLite 行，而 analyzeProject 检查的是 activeAnalyses Map。
  • 步骤 5 依赖 analysisStartedAt。init effect 的依赖数组包含 project?.analysisStartedAt，确保同一个 projectId 重新分析时也能重置 hasStarted.current 等 ref。
  • 步骤 7 的管线会检测 checkpoint。如果 media-manifest.json 和 frames-checkpoint.json 存在且版本匹配，跳过对应阶段并发送"恢复进度"消息。这是"清缓存后还看到旧日志"的感知来源。

09缓存层次与"清除"的含义

用户说"清除缓存"可能指 SettingsScreen 里的 LLM 响应缓存清除。但 ClipIQ 实际上有三层缓存，每层清除的范围不同：

缓存层 存什么 清除操作 重新分析影响
LLM 响应缓存 prefilter / shot-merger / summarizer / main-analysis 各阶段的 LLM 调用结果 Settings → "清除缓存" LLM 阶段重跑，但抽帧/字幕仍复用
Checkpoint 文件 media-manifest.json / frames-checkpoint.json 无 UI 入口（手动删文件） 视频检测 / 抽帧从头跑
Artifact 文件 artifacts/ 目录（帧图 / 音轨 / transcript） 删除项目、或手动删 artifacts/ 所有阶段从头跑
用户感知 GAP
Settings 里"清除缓存"只清 LLM 层。重新分析时管线检测到 checkpoint + artifacts 仍在，跳过抽帧和字幕，直接从 LLM 分析开始。管线发出的"恢复进度 · 跳过抽帧，复用 20 张已有关键画面"消息虽然是新日志，但用户认为这是"上次留下来的"——因为他们预期"清缓存 = 完全从头来"。

10已知问题与已修复的 Bug

Bug 1: 进度值回退 (已修复)

弹幕情绪聚合的进度序列是 94 → 95 → 89 → 97。第三步的 89 低于前一步的 95，导致进度条从 95% 回退到 89% 再跳到 97%。

修复：electron/main.cjs:5043 的 send(89, ...) 改为 send(96, ...)，确保单调递增。

Bug 2: ProgressScreen 重试不重置 ref (已修复)

当用户在 ProgressScreen 内点"重试"时，routeKey 不变（始终是 analysis:progress），ProgressScreen 不卸载重挂。此时 init effect 只依赖 [project?.id]，同一 projectId 不触发重跑，hasStarted.current 残留为 true，kickoff effect 早退。

修复：init effect 依赖数组加入 project?.analysisStartedAt。startAnalysisForProject 每次调用都会更新 analysisStartedAt 为新时间戳，保证 init effect 重跑、所有 ref 重置。

感知问题: "旧日志"

这不是代码 bug，而是 checkpoint 复用的正常行为。logsByProject 确实被清空了，但新管线检测到有效的 checkpoint 文件后跳过了抽帧和字幕阶段，发出的"恢复进度"消息看起来像是旧日志。如果需要完全重跑，需要同时删除 checkpoint 文件和 artifacts 目录。
